## Шаг 2 (2026-10-27, Windows 10, ВМ не работали, загрузка CPU < 2%)

- H0 пройден: 200 тестов OK за 42 с (Python 3.10.22 через uv). Код проекта на stdlib работает в Windows без правок.
- Зонд (`probe.json`): 192 логических процессора, один «узел» 0-191, поля lscpu, numactl и dmidecode пусты (на Windows их нет). Данные об узлах и слотах берутся из шага 1.
- Кривая «задач/с» (SHA-256 по 2 МБ в потоках, считает процессор, не память):

| потоков | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|---|
| задач/с | 760 | 1434 | 2972 | 4940 | 8052 | 15178 | 15206 |

- Масштабирование почти линейно до 32 потоков, дальше нуля прироста: излом 32.
- «Полоса памяти» 34.6 ГБ/с — копирование одним потоком, а не полоса узла; с расчётными 94 ГБ/с первого сокета не сравнивать.

## Шаг 3 (llama.cpp b11351, CPU-бэкенд haswell/AVX2, Llama-3.2-1B Q4_K_M, 0,8 ГБ)

- Windows показывает 3 группы и 4 узла: 64 + 64 + 32 + 32 логических процессора. Предположительно узлы 0 и 2 (64 + 32) — сокет с памятью, 1 и 3 — пустой сокет.
- Гипотеза «процесс видит 64» опровергнута для llama.cpp: при `-t 96` заняты ровно узлы 0 и 2 (100%), узлы 1 и 3 простаивают (0–3%). Питон-зонд упёрся в 32 потока по другой причине (он не знает о группах).
- Скорость, ток/с:

| потоков | 8 | 16 | 32 | 48 | 64 | 96 |
|---|---|---|---|---|---|---|
| генерация tg64 | 44,7 | 46,1 | 42,6 | 39,9 | 37,4 | 34,7 |
| промпт pp128 | 342 | 621 | 836 | 859 | 936 | 898 |

- Генерация достигает 46 ток/с на 16 потоках и дальше падает; критерий ≥ 10 ток/с выполнен с запасом. Промпт растёт до 64 потоков.
- 46 ток/с × 0,8 ГБ ≈ 37 ГБ/с эффективной полосы, заметно ниже расчётных 94: один экземпляр не выбирает память сокета. Значит, выгоднее несколько экземпляров по 8–16 потоков, чем один на все ядра. Проверяется в шаге 4.
- Парсер `hw_llama.py --parse` отработал на настоящем выводе: максимум 46,05 ток/с на 16 потоках, излом на 8 потоках.

## Шаг 4 (несколько экземпляров, организм на модели)

- Суммарная генерация при N экземплярах по 16 потоков: 1 → 43,4; 2 → 46,8; 4 → 47,6; 6 → 50,9 ток/с. Рост почти нулевой.
- Все 6 экземпляров (96 потоков) легли на узел 0 (64 процессора, загрузка 100%), остальные узлы простаивали. Windows кладёт процесс на один узел, поэтому рост сумм упёрся в процессоры и память одного узла, а не всего сервера. Чтобы расселить экземпляры по узлам, нужна явная привязка (`start /node N`, шаг 5).
- Оценка эффективной полосы одного экземпляра: 43 ток/с × 0,77 ГБ ≈ 33 ГБ/с, совпадает с копированием зонда (34,6 ГБ/с). Куда упираемся (узел, память сокета, связь между сокетами), пока не доказано.
- Организм на настоящей модели работает (`hw_live.py`, 1B Q4): `last_tps` 41,5, слоты AIMD 4 из 4, задержка цикла 25,7 мс, пачка из 4 запросов за 2,3 с. Критерий H4 выполнен механикой.
- Качество: 1B не держит конверт ответа. На просьбу выполнить команду пришло «0,99», в тексте вкрапления чужих языков. Нужна модель крупнее (A3B) и запасной разбор ответа, если конверта нет.
- Ошибка шаблона `go.md`: `break` внутри `ForEach-Object` завершил весь скрипт. Для ожидания использовать цикл `while`.

## Доработки зонда (не срочно)

- Расширить кривую потоков до числа логических процессоров (сейчас максимум 64).

- Писать отчёты в UTF-8: `Tee-Object` в PowerShell 5.1 даёт UTF-16.
