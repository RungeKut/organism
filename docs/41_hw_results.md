## Шаг 2 (2026-10-27, Windows 10, ВМ не работали, загрузка CPU < 2%)

- H0 пройден: 200 тестов OK за 42 с (Python 3.10.22 через uv). Код проекта на stdlib работает в Windows без правок.
- Зонд (`probe.json`): 192 логических процессора, один «узел» 0-191, поля lscpu, numactl и dmidecode пусты (на Windows их нет). Данные об узлах и слотах берутся из шага 1.
- Кривая «задач/с» (SHA-256 по 2 МБ в потоках, считает процессор, не память):

| потоков | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|---|
| задач/с | 760 | 1434 | 2972 | 4940 | 8052 | 15178 | 15206 |

- Масштабирование почти линейно до 32 потоков, дальше нуля прироста: излом 32.
- «Полоса памяти» 34.6 ГБ/с — копирование одним потоком, а не полоса узла; с расчётными 94 ГБ/с первого сокета не сравнивать.

## Гипотеза: процесс видит одну группу процессоров

Windows делит 192 логических процессора на группы по не более чем 64, а процесс по умолчанию живёт в одной группе. Тогда излом на 32 потоках — это 32 ядра группы с SMT, а не потолок железа. Согласуется с данными, но не доказана. Проверка в `go.md` шага 3: загрузка по каждому логическому процессору во время замера и привязка процессоров к узлам NUMA из счётчиков `Processor Information`.

Следствие, если гипотеза верна: один процесс llama.cpp в Windows использует не больше 64 потоков, а для всего первого сокета нужны несколько экземпляров, по одному на группу. Это совпадает с замыслом организма (много маленьких специалистов).

## Не получено

- WSL: дистрибутив не зарегистрирован, нужна перезагрузка сервера (делает человек, по желанию).
- Карта узлов и расстояния NUMA, пустые слоты: нужны Linux или счётчики Windows (шаг 3).
- Скорость llama.cpp: модель и сборка на сервере появятся в шаге 3.
